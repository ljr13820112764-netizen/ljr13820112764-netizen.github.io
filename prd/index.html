2.3核心价值（一句话）

准绳是一本规范驱动的整改留痕本：发现问题 → 记一条整改记录 → AI 自动关联规范条文作为处置依据 → 整改前/后照片留痕 → 一键导出存档。问（查规范）→ 记（整改记录）→ 引（条文依据）→ 留（前后影像）→ 出（导出留档）——五个现场高频动作，一个产品闭环。

🛠 土木批注：对比 v1.2 的「查 → 问 → 存 → 写」——v2.0 的价值链把落脚点从"写"改成了"出（导出留档）"。这个改动是整个定位重构的核心：v1.2 的闭环终点是"沉淀在自己的笔记里"，v2.0 的终点是"拿出一份带条文出处的可交付物"。前者是自我满足，后者有真实的交付对象（质检、监理、下次检查）——有交付对象，产品才有存在理由。

2.4定位变更说明（v1.2 → v2.0 的决策过程）

v2.0 的定位重构不是拍脑袋，而是经过一次三视角产品评审后的收敛：

评审视角 核心问题 结论
用户价值核算（价值公式 + 替换成本） 相比现状替代（群聊 + 水印相机 + 纸质日志 + 免费日志 App），新体验增量在哪？ 四个候选方向中，只有「整改前后记录」的账算得过来：旧体验最差（群聊翻照片）、替换成本最低（单边可用，不依赖他人装 App）
证据分级（Mom Test 纪律） 哪些方向有行为证据？哪些是自我投射？ 四个候选方向全部只有作者单信源、无代价级证据——因此全部标注假设，裁剪验证计划（4.4）
风险取舍（四大风险） 哪个方向碰得过？哪个碰不过？ 防篡改水印（授时+验真）和日历提醒（系统日历已解决）为负期望，砍除；差异化必须站在"条文"上

收敛结果：产品定位从「工程人工作笔记软件」（无行为证据的宽定位）收窄为「规范驱动的整改留痕助手」（有行为证据的场景 + 有壁垒的能力交叉点）。被砍项的完整论证见 4.3。

定位广度（v2.2 补）：收敛的是「场景」，不是「专业」——「整改留痕 + 条文挂载」对房建、市政、机电、钢结构、风电等各专业一线施工员同等成立；作者的海上风电项目背景是产品的起源场景，不是产品的边界。产品面向所有工程人，演示数据与示例须覆盖多专业（要求见 4.2）。该定位为推论、非已验证事实（v2.2.1 补注，评审 S7）——验证方式见 2.1 A6（访谈 ≥2 名非风电一线）。

🛠 土木批注：这一节是 v2.0 的"设计说明图"——工程施工前要审图，产品动工前要审方向。注意结构：先列评审判据、再给结论、最后指向砍项论证，三步让评审者不用翻遍全文就能确认"这个收缩是算过账的"。作品集里呈现这种"决策可审计"的结构，比多写三个功能更有说服力。

4.3主动砍掉什么、为什么（v2.0 新增）

本节回答一个问题：为什么不把四个方向都做了？ 每个"砍"都有独立的判断依据，可直接在评审会上复述。

# 被砍 / 降级项 原设想 决定 理由
1 防篡改水印 参照「今日水印相机」做时间地点防篡改水印照片 降级为普通照片附件；明确不做防篡改 ① 防篡改的壁垒不在水印样式，在「真实时间地点」的信任背书（国家授时+验真机制），单人作品无法复刻；② 更要紧的是：一个无法验真的水印会暗示它没有的证据效力——在工程质量语境里，这从"功能不足"变成"诚信问题"；③ 照片本身（前后对比+图注）已满足个人留档需要
2 日历式会议提醒 例会/交底会日历提醒 + 联动会议纪要 砍除 ① 手机系统日历已解决提醒需求，新体验增量≈0；② 该方向无任何行为证据（访谈无记录）；③ 与"规范/条文"核心能力零关联。会议纪要保留（含在笔记容器中）
3 「工作笔记软件」定位词 产品定位为"工程人要用的工作笔记软件" 弃用，改为「规范驱动的整改留痕助手」 无"主动写笔记"的行为证据支撑宽定位；四个功能的实质是"合规留痕"而非"笔记"，定位必须与功能自洽（v1.2 的"笔记本"心智保留为容器，不升级为卖点）
4 水印照片独立模块 作为独立功能模块建设 并入照片附件能力 独立模块=一条独立产品线；附件=一项基础能力。不给"红海且无壁垒"的能力以模块级投入
5 多人整改流转 整改人→复查人完整闭环（对方接收、复查确认） 推迟至产品化阶段 ① MVP 单边即可成立（自己记录自己导出）；② "对方愿意装 App 并在系统内响应"是未验证的信任假设（4.4 H3），不拿 MVP 赌它

🛠 土木批注：这一节是评审会上最有杀伤力的部分。工程语境里最能说明问题：一份标书写"我们做了 12 项"不如写"这 5 项为什么不做"——前者是功能清单，后者是判断力。注意每条砍项的理由结构：先说替代方案的现实（别人已经解决/壁垒在哪）→ 再说自己的边界（复刻不了/无证据）→ 最后说留下的部分怎么满足需求。这个三段式可以直接复用到任何"需求砍除"汇报。

5.3功能二：条文自动挂载（P0，差异化核心，已实现）

功能描述

用户填写「问题描述」时，系统基于描述中的关键词/语义检索规范库，推荐 Top 3 相关条文（含规范名/条文号/原文摘要；展示于定高 56px 常驻条带——默认展示第 1 条 + 「共 n 条」展开，空间模型见 5.1）；用户一键采纳后，条文以「处置依据」形式挂载到整改记录（复用 v1.2 的 cite-inline 引用组件与条文详情链路）。这是本产品与其他工具的本质差异：整改记录自带"处置依据"，而非只有照片和文字。

操作流程

  1. 用户在「问题描述」输入（如「混凝土浇筑后未按要求保湿养护」（房建）／「管道灌水试验未做」（机电）／「吊装警戒区隔离范围不足」（钢结构·吊装）——推荐机制不分专业）
  2. 停止输入后（防抖 ~800ms），系统检索条文库 → 推荐清单出现在描述框下方
  3. 用户点击某条推荐的「引用」→ 该条文以引用样式插入「依据条文」区
  4. 用户可继续补充/删除条文；也可从规范库手动添加

业务规则（v2.1 修订）

  • 规则 1：推荐结果必须来自条文库数据，不得由模型生成条文号（沿用 v1.2 铁律）
  • 规则 2：推荐默认 Top 3，标注「推荐」标签（条带内默认展示第 1 条 + 「共 n 条」展开，见 5.1）；用户未采纳不做静默挂载；推荐卡固定文案「AI 推荐仅供参考，请核实后采用」（评审 M7）
  • 规则 3（v2.1 细化，评审 M4；v2.2.1 实测核对）：原型期复用规范库既有检索链路（与问答模块同一关键词路由实现）+ 随原型交付演示映射表——实测现为 39 条（代码注释旧称"约 20~30 条"已滞后，以实测为准）；v2.2 扩充至 ≥60 条、覆盖 8 组规范（见 5.7 规则 6）——2026-10-06 回填：已扩充至实测 69 条、覆盖 8 组；产品化期接 RAG 同链路
  • 规则 4：条文状态标签沿用 v1.2 体系（现行有效 / 内部文件）；演示库已不含「厂家手册」类条目（见 v2.1.3 修订记录）
  • 规则 5（快照落库，评审 B8）：采纳的条文以快照结构 {clause_id, 快照原文, adopted_at, adopted_via} 存入记录——条文库此后更新不影响历史记录；详情页与导出一律读快照（留痕产品可信性的根基）
  • 规则 6（防陈旧结果，评审 M4）：查询携带请求序号，仅渲染最新序号的返回；描述编辑后自动重新推荐（同一防抖 800ms + 序号机制），已采纳的条文不因重推被移除；已采纳条文的文本不参与后续匹配（防自我增强——与 5.7 推荐排序排除口径一致，v2.2.1 核验收口）
  • 规则 7（版权声明，评审 M7；v2.2.1 承接口径统一）：条文详情页注明「条文版权归发布机构所有，仅供个人工作参考」；导出物按 5.5 规则 2 第⑥要素承接——含条文时统一附加同一版权句

🛠 土木批注：这个功能的写法要点是"设计一个不存在的技术也可信"——原型期用关键词匹配、产品化接 RAG，和问答模块同一条演进路线。面试时这条链路会被追问（"你怎么保证推荐的条文是对的？"），答题要点在规则 1 和 2：不生成条文号 + 不静默挂载，人始终在环里。AI 辅助留痕的边界感就是这个。
